Lock — must learn

A lock is a variable associated with a data item that describes the status of that item with respect to the operations that may be applied to it. It is the mechanism used to synchronize access by concurrent transactions. A transaction cannot read or write an item until it acquires an appropriate lock, and all lock requests go to the concurrency-control (lock) manager.

Binary locks

Two states: locked (1) and unlocked (0). Operations: lock_item(A), unlock_item(A).

#Rule every transaction must obey
1Issue lock_item(A) before any read or write of A.
2Issue unlock_item(A) after all reads/writes of A are completed.
3Do not lock A if the lock on A is already held.
4Do not unlock A unless the lock is held.
5The lock manager enforces these rules; at most one transaction holds a lock on an item.

Drawback: too restrictive — it enforces mutual exclusion even for two readers, so it is not used in practice.

Shared / exclusive locks

  • Shared lock S (read lock) — lock-S(Q): item may be read by several transactions; cannot be updated.
  • Exclusive lock X (write lock) — lock-X(Q): item may be read and written, but by one transaction only.
  • unlock(Q) releases either mode.
Compatibility: can the request be granted?
Held ↓ / Requested →SX
S✓ granted✗ wait
X✗ wait✗ wait

Two readers never conflict; a write conflicts with every other access. If a lock is incompatible, the requesting transaction waits until the holder releases it.

Four lock-based protocols Must learn

ProtocolRuleEffect / drawback
SimplisticLock every object before beginning an operation; unlock after the write is finished.Simple but too many locks; no serializability guarantee.
Pre-claimingList all items needed, request all locks before execution. If all are granted the transaction runs; if not, it rolls back and waits. All locks released at the end.Deadlock-free (no waiting while holding), but poor concurrency and wasted work.
Two-phase locking (2PL)Growing phase: acquire locks, release none. Shrinking phase: release locks, acquire none. The first unlock ends the growing phase.Guarantees serializability; does not guarantee deadlock freedom.
Strict 2PLSame as 2PL, but no lock is released until commit; all locks are released together.No shrinking phase, hence no cascading abort; still deadlock-prone.

Lock conversion

  • Upgrade S(a) → X(a) is allowed only in the growing phase.
  • Downgrade X(a) → S(a) must be done in the shrinking phase.
Check this point The source summary says “2PL needs a transaction to acquire a lock after it releases one of its locks”. That is the opposite of the protocol. Correct statement: after releasing any lock, a transaction can acquire no new lock.

Implementation: lock manager and lock table

The lock manager handles lock/unlock requests by message passing with transactions. Its data structure is the lock table:

  • A hash table indexed by the name of the data item.
  • Each locked item heads a linked list of requests.
  • Each node stores: transaction id, lock mode (shared/exclusive), status (granted/waiting).
  • New requests are appended at the end of the list (queue).
  • Hash collisions are handled by separate chaining.

Working of the lock manager

  1. Table starts empty (nothing locked).
  2. Request for Q: if Q is free, create the list and grant the lock.
  3. If Q is locked, append a node; grant it immediately if the mode is compatible, otherwise mark it waiting.
  4. On unlock, delete that node and grant the lock to the next compatible waiting transaction.
  5. On abort, delete all of the transaction's waiting requests, then release its held locks.

Starvation and deadlock

Starvation

A transaction waits for an indefinite period to acquire a lock. Causes: waiting scheme not managed properly; resource leak; the same transaction chosen as victim repeatedly.

Deadlock

Two or more transactions wait for each other to release resources in a circular chain, so none can proceed. Handled by rolling back a victim (local/global deadlock detectors in distributed systems).

Design conclusion (from the source): not using locks gives inconsistent states; unlocking too early also gives inconsistent states; never unlocking before requesting the next lock causes deadlock. Deadlock is preferable to inconsistency because a deadlock can be resolved by rollback, while an inconsistent database may cause real-world damage.
