Query processing — must learn

Query processing is the set of steps a DBMS performs to turn a high-level query (SQL) into an execution plan and then into a result. Query optimization is the step that chooses the cheapest of several equivalent plans for the same query — equivalent because relational algebra expressions can be rewritten without changing the result.

Steps in query processing

  1. Parsing and validation — the parser checks syntax; the catalog is checked for the existence of relations and attributes; the user's authorisation is verified.
  2. Translation — the validated query is converted into a relational algebra expression (a tree of σ, π, ⋈, ×, ∪ …).
  3. Optimization — equivalent plans are generated and their costs estimated; the cheapest plan is kept.
  4. Evaluation — the execution engine runs the plan with physical operators (table scan, index scan, sort, hash join …) and returns the result.

A query evaluation plan is the annotated tree: each algebra operation is mapped to a concrete algorithm plus an access path.

Cost model and catalog statistics

  • Cost is measured mainly in block (page) transfers from disk; CPU time and, in distributed systems, communication cost are added.
  • The catalog stores statistics: nr tuples, br blocks, sr tuple size, fr tuples per block, V(A, r) distinct values of A.
  • Selectivity = fraction of tuples that satisfy a condition. For an equality on a non-key attribute: nr / V(A, r).
  • Statistics are approximate and refreshed periodically, so the optimizer's choice can be wrong for skewed data.

Heuristic (rule-based) optimization

  1. Push selections down — apply σ as early as possible, before joins, so fewer tuples flow upward.
  2. Push projections down — drop unused attributes early, reducing tuple width.
  3. Turn σ over × into a join — never compute a Cartesian product when a join condition exists.
  4. Join the most restrictive pair first — smallest intermediate results.
  5. Use an index for a selection or join predicate when one exists.
  6. Reuse common sub-expressions; avoid computing the same result twice.

Cost-based optimization

  • Enumerate the search space: join orders, join algorithms, access paths (index or scan), and pipelining choices.
  • Estimate the cost of each candidate with the catalog statistics and keep the cheapest.
  • Dynamic programming (System R): build left-deep join trees, and for every subset of relations keep only the cheapest plan — n relations give 2n subsets instead of n! orders.
  • Cost grows quickly, so real optimizers use heuristics to prune the space before costing.

Pipelining vs materialization

  • Pipelining — a parent operator consumes tuples as the child produces them; no temporary relation is written. Cheaper, but blocked by sort and hash operators.
  • Materialization — the intermediate result is written to a temporary relation and read back; needed when the consumer needs the whole input first.

Exam focus — Query processing
  • 2 marks: define query processing and query optimization; name the four steps.
  • 5 marks: the four steps with a diagram, or the six heuristic rules with one example each.
  • 10 marks: definition → four steps and diagram → cost model and statistics → selection and join tables → heuristic rules → cost-based optimization → one worked example comparing two plans.
  • Likely questions: (i) Why is a Cartesian product avoided when a join condition exists? (ii) Compare nested-loop, sort–merge and hash join. (iii) Cost a block nested-loop join for given br and bs. (iv) Pipelining vs materialization?
