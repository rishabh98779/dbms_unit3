6§S06 Timestamp Ordering source 3.2.7

Timestamp — must learn

A timestamp TS(T) is a unique identifier created by the DBMS for each transaction, usually assigned in the order in which transactions are submitted (system time or a logical counter). The protocol orders transactions by timestamp, so the only permitted equivalent serial schedule is the timestamp order. The older transaction always gets priority.

Two timestamps per data item X

W_TS(X)Largest timestamp of any transaction that successfully wrote X.
R_TS(X)Largest timestamp of any transaction that successfully read X.

Basic TO — write rule

When T issues write(X):

  • If R_TS(X) > TS(T) or W_TS(X) > TS(T) → a younger transaction has already read/written X, so abort and roll back T, reject the operation.
  • Otherwise execute the write and set W_TS(X) = TS(T).

Basic TO — read rule

When T issues read(X):

  • If W_TS(X) > TS(T) → a younger transaction has already written X → abort and reject T.
  • Otherwise execute the read and set R_TS(X) = max(TS(T), R_TS(X)).

How to answer a numerical question

T1: TS = 0010   T2: TS = 0020   T3: TS = 0030
Priority: T1, then T2, then T3.

Case: R_TS(X) = 30, W_TS(X) = 10
  T2 writes X → R_TS(X)=30 > TS(T2)=20
  ⇒ abort T2 (a younger T3 already read X).

Case: W_TS(X) = 10
  T2 reads X → 10 ≤ 20 ⇒ read allowed,
  R_TS(X) = max(20, 30) = 30.

The algorithm compares TS(T) with R_TS(X) and W_TS(X) on every read and write, and rejects the operation of the transaction that would violate the order.

Strict TO

A transaction T that issues read(X) or write(X) with TS(T) > W_TS(X) has its operation delayed until the transaction that wrote X has committed or aborted. This makes schedules both strict and conflict serializable, and removes cascading rollback.

Advantages / disadvantages Must learn

AdvantagesDisadvantages
Schedules are conflict serializable (precedence graph is acyclic).Basic TO can still cause cascading rollback, so schedules may not be recoverable.
Deadlock-free: no transaction ever waits.Starvation possible if the same transaction is restarted and continually aborted.

7§S07 Optimistic Control, Granularity & Distributed CC source 3.2.8

Granularity of data items

The granularity is the size of the data item chosen as the unit of protection by the concurrency-control protocol. Possible levels, coarse → fine: whole database → file → page (area) → record → field.

Coarser granularityFiner granularity
Lower degree of concurrency (a lock on a block blocks other records in it).Higher concurrency (different records lock independently).
Less lock information to store, fewer lock operations.More items, more locks, bigger lock table, more overhead.

Best size depends on the transaction mix: few records per transaction → record level; many records of one file → block or file level.

Intention locks

To make multi-level locking practical, a transaction announces on the path from root to node what it will do below:

  • IS — intention shared: shared locks will be requested on descendants.
  • IX — intention exclusive: exclusive locks will be requested on descendants.
  • SIX — shared + intention exclusive: the node is locked in shared mode and exclusive locks will be requested below.

Multiple granularity locking (MGL) rules

  1. Respect the lock compatibility table.
  2. The root must be locked first, in any mode.
  3. Lock a node in S or IS only if the parent is already locked in IS or IX.
  4. Lock a node in X, IX or SIX only if the parent is already locked in IX or SIX.
  5. A transaction may lock a node only if it has not yet unlocked any node (2PL).
  6. Unlock a node only when none of its children are still locked by that transaction.

Benefit: a mix of short record-level transactions and long file-level transactions runs with less blocking and less locking overhead than single-level locking.

Optimistic (validation-based) concurrency control Must learn

Also called validation or certification. No checking is done during execution; updates are applied to local copies and the serializability test is postponed to just before commit. It is called “optimistic” because it assumes little interference.

  1. Read phase — read committed values from the database; all updates go to local copies (transaction workspace).
  2. Validation phase — check that applying the updates will not violate serializability.
  3. Write phase — if validation succeeds, apply the updates to the database; otherwise discard them and restart the transaction.

Three validation rules

  • Rule 1 — if Ti reads what Tj writes, Ti's execution must not overlap Tj's commit; Tj commits only after Ti finishes execution.
  • Rule 2 — if Ti writes what Tj reads, Ti's commit must not overlap Tj's execution; Tj starts only after Ti has committed.
  • Rule 3 — if Ti and Tj both write the same item, their commit phases must not overlap; Tj commits only after Ti has committed.

Practical check for Ti: validated if, for every committed/validating Tj, (1) Tj finished writing before Ti started reading, or (2) Ti starts writing after Tj finished writing and read_set(Ti) ∩ write_set(Tj) = ∅, or (3) both sets of Ti are disjoint from write_set(Tj) and Tj finished reading before Ti did.

Works well at low conflict rates (few aborts, almost no overhead during execution). At high conflict rates many completed transactions are discarded and restarted, so it performs badly.

Concurrency control in distributed systems

ApproachKey points
Distributed timestampA local clock is not globally unique, so a timestamp = site ID + that site's clock reading. Each site's scheduler keeps one queue per transaction manager; requests are queued in increasing timestamp order and processed oldest first.
Conflict graphsA transaction class is defined by a read set and a write set; a transaction belongs to the class if its sets are subsets of the class sets. Vertical edge = conflict within a class, horizontal edge = write–write conflict across classes, diagonal edge = read–write/write–read conflict across classes. The graph tells whether two transactions can run in parallel.
Distributed optimisticRule 1: validate locally at every site where the transaction executed; invalid at any site ⇒ abort. Rule 2: after local validation, validate globally so that conflicting transactions commit in the same relative order at all sites — this may force a wait, making the algorithm less optimistic.
