1§S01 Transactions & ACID source 3.2.1 – 3.2.2

Definition — must learn

A transaction is a group of tasks (a program unit) executed as a single logical unit whose execution may or may not change the contents of the database. It is a set of changes that must all be made together: either every operation is executed, or none is. If the database was consistent before the transaction, it must be consistent after it.

Why “all together” — the transfer example

A bank employee transfers Rs 500 from A to B. This “simple” transaction is several low-level tasks:

A's account
  Open_Account(A)
  Old_Balance = A.balance
  New_Balance = Old_Balance - 500
  A.balance   = New_Balance
  Close_Account(A)
B's account
  Open_Account(B)
  Old_Balance = B.balance
  New_Balance = Old_Balance + 500
  B.balance   = New_Balance
  Close_Account(B)

If the machine crashes between the two updates, money is lost (debit done, credit not done). Doing the credit first gives the customer free money. Hence both changes must succeed or both must fail.

Process: read and write

  • Read: the object is brought from disk into main memory, and its value is copied into a program variable.
  • Write: the in-memory copy of the object is modified, then written back to disk.

Transaction operations

begin_transactionMarker: transaction execution starts.
read_item(X)Reads database item X into a program variable.
write_item(X)Writes the modified value of X to the database.
end_transactionMarker: transaction execution ends.
commitAll operations completed; changes are permanent and cannot be undone.
rollbackTransaction unsuccessful; all temporary changes are undone.

ACID properties Must learn

PropertyMeaningGuarantee / who ensures it
Atomicity
“all or nothing”		Either all operations of the transaction are performed or none. No state where a transaction is half-completed.Maintained by the recovery-management component: it keeps old values of any write and restores them if the transaction does not complete.
Consistency
no integrity violation		A transaction must preserve database consistency. In the transfer example, A + B must be unchanged.Responsibility of the application programmer who writes the transaction (the DBMS assumes it holds).
Isolation
concurrent changes invisible		Concurrent transactions must behave as if executed serially in some order. Data used by one transaction cannot be used by a second until the first finishes.Responsibility of the concurrency-control component (locks, timestamps, validation).
Durability
committed updates persist		Once committed, the effect of the transaction is never lost, even after a later crash.Responsibility of the recovery-management component (logs on stable storage, checkpoints).

Example of a failed isolation: T1 transfers 50 (A: 1000→950, B: 2000→2050) while T2 reads A and B mid-way and prints 2950 instead of 3000.

States of a transaction Must learn

StateMeaning
ActiveInitial state; the transaction is executing.
Partially committedAfter the final statement has been executed. Output may still be in main memory, so the transaction can still fail.
FailedNormal execution can no longer proceed (a recovery-system check failed).
AbortedAfter rollback; the database is restored to its state before the transaction started. Then restart or kill.
CommittedAfter successful completion; effects are permanently established.

A transaction is terminated if it has committed or aborted. A transaction can be committed only if it has entered the committed state.

Schedules and conflicts

A schedule is the total order in which the operations of several transactions appear for execution.

  • Serial schedule: only one transaction is active at a time; no overlap.
  • Parallel (non-serial) schedule: more than one transaction is active; operations overlap in time.
Conflicting operations — 3 conditions

Two operations conflict when (1) they belong to different transactions, (2) they access the same data item, and (3) at least one is a write. Read–read never conflicts.
