8§S08 Database Recovery source 3.3.1 – 3.3.3

Definition — must learn

Database recovery is the process of restoring the database to its correct (last consistent) state after a failure — a system crash, transaction error, incorrect command, virus, hacking, disk damage or a catastrophic event — so that committed work is never lost and no transaction is left half-done.

Why recovery is needed

  • Data must be available whenever it is required; a DBMS must hold tools that recover data efficiently.
  • It must guarantee atomicity: a transaction's effects are either permanently recorded or absent.
  • Dependability = the flexibility of the DBMS to different failures plus its ability to recover from them.
  • Two things must be considered whatever the cause: failure of main memory (including database buffers) and failure of the disk copy of the database.

Sources of failure (3.3.1)

  • Hardware/software errors → system crash → loss of main memory.
  • Media failure (head crash, unreadable media) → loss of part of secondary storage.
  • Application software/logical errors → transactions abort.
  • Natural disasters: fire, flood, earthquake, power failure.
  • Carelessness of operators/users; malicious corruption (viruses).

Classification of failures

TypeMeaning and causes
Transaction failureA transaction must terminate because it cannot proceed. Logical error — bad code or an internal error condition. System error — the DBMS cannot execute the active transaction or must abort it (e.g. resource problem). Only a few transactions are affected.
System crashExternal problems stop the system abruptly: power interruption, OS error, hardware failure. Main memory (and buffers) are lost; disk survives.
Disk failureBad sectors, disk inaccessibility, head crash, or any failure that destroys all or part of disk storage. Requires restoring from backup.

Storage structure

TypeBehaviourExamples
VolatileCannot survive a system crash; close to the CPU.Main memory, cache memory
Non-volatileSurvives a crash; large capacity but slower access.Hard disks, magnetic tapes, flash memory
Check this point The source lists RAM as an example of non-volatile storage. That is wrong — RAM is volatile. Write “hard disk, magnetic tape, flash memory” in the exam.

FacilityPurpose

Recovery managerRestores the database to a consistent state after any failure.

Log-based recovery Must learn

A log (system log / journal) is a sequence of records describing every operation that affects database values, kept on stable storage. A log record is written before the database is modified (write-ahead rule).

RecordMeaning
<Ti, Start>Transaction Ti has started.
<Ti, Xj, V1, V2>Ti wrote Xj: V1 = old value (before image), V2 = new value (after image).
<Ti, Commit>Completed successfully; effects are permanent.
<Ti, Abort>Rolled back; effects must be removed.

Deferred vs immediate database modification Must learn

PointDeferred modificationImmediate modification
When is the database written?Only after the transaction reaches its commit point; before that, updates stay in the local workspace / log.While the transaction is still active — each write is applied to the database as soon as it is logged.
Log needsNew value is enough (old value not needed for undo).Both old and new values: <Ti, Xj, V(old), V(new)>.

Other nameNo-undo / redo algorithmUndo / redo algorithm

Worked log (A = B = 1000 initially)

T1: <T1,Start>  <T1,A,1000,900>  <T1,B,1000,2100>  <T1,Commit>
T2: <T2,Start>  <T2,C,3000,2800>  <T2,Commit>

Crash after <T2,C,3000,2800>, before <T2,Commit>
→ T1: start + commit  ⇒ REDO  (A=900, B=2100)
→ T2: start, no commit ⇒ UNDO  (C back to 3000)
Final: A=900, B=2100, C=3000

Redo re-applies new values; undo restores old values. Undo is done first, then redo. Repeating undo/redo must give the same result as doing it once.

Crash cases to write in the exam

  • Immediate mode, crash after commit → log has Start + Commit → REDO(T) sets the new values of A and B.
  • Immediate mode, crash before commit → log has Start but no Commit → UNDO(T) restores old values, because the updates were already written to the database.
  • Deferred mode, crash after commit → REDO(T) applies the logged new values.
  • Deferred mode, crash before commit → nothing to undo (the database was never touched); the incomplete log is ignored.
Check this point One passage of the source says that in deferred mode, on failure before commit, the recovery manager “will set the old value of data items”, and the next note says no UNDO is needed. The note is correct: in deferred mode the database still holds the old values, so no undo action is required.

Checkpoints

Keeping every log in memory forever is impossible. A checkpoint is a point at which all previous logs are removed from the system and stored permanently on disk; it declares a point before which the DBMS was in a consistent state and all transactions were committed.

Actions performed at a checkpoint

  1. Write the checkpoint start record, with time and date, to the log on stable storage.
  2. Copy all log records from memory buffers to the log on stable storage.
  3. Write modified database buffers out to the physical database.
  4. Write an end-of-checkpoint record and save its address where the recovery routine can find it at start-up.

Undo list / redo list

  • Redo list: transactions with <Ti, Start> and <Ti, Commit> (or just a commit record).
  • Undo list: transactions with <Ti, Start> but no commit or abort record.

Checkpoint frequency is a design choice: fixed time interval, transaction-consistent, action-consistent, or transaction-oriented checkpoint.

  • T1 — committed before the checkpoint → nothing to do.
  • T2 — committed after the checkpoint → REDO.
  • T3 — started after the checkpoint and commits → REDO.
  • T4 — no commit record → UNDO.

Shadow paging, caching and backups

Shadow paging

  • The database is divided into fixed-length pages. A page table with n entries points to the n pages.
  • At the start of the transaction, the current page table is copied to a shadow page table; both are identical.
  • During execution the current table is changed; the shadow table stays as it was.
  • When the changes are ready to become durable, the directory is updated to point to the new pages; on failure the shadow table restores the old state.
  • Provides atomicity and durability with less disk access than log methods.

Caching / buffering

Disk pages holding items to be updated are cached in main-memory buffers (the DBMS cache). A directory tracks which items are in the buffer, and each buffer has a dirty bit: 0 = not modified, 1 = modified and must be written back.

Backup techniques

TypeWhat it stores
Full backupThe whole database plus the metadata needed to restore it (including full-text catalogs), taken at predefined intervals.
DifferentialOnly changes since the last full backup; if an item changed many times, the most recent version is stored. A full backup must be restored first.
Transaction logEvery log entry / statement executed. Allows recovery to a specific point in time; even if data files are destroyed, no committed transaction is lost.

Recovery procedure in words: restore the last full backup → apply the latest differential backup → roll the transaction log forward to the desired point in time.
