3§S03 Recoverability source 3.2.4

A transaction may fail (hardware failure, system crash, software issue) and must be rolled back. If another transaction already read a value produced by the failed transaction, that reader must be rolled back too. Recoverability classifies schedules by whether this rollback is still possible.

Recoverable schedule — must learn

A schedule in which a transaction commits only after every transaction whose changes it read has committed. Formally: if Tj reads a value written by Ti, then commit(Tj) must occur after commit(Ti).

Schedule typeConditionWhat happens on failure of Ti
IrrecoverableTj reads the value updated by Ti and commits before Ti commits/aborts.Ti fails later; Tj has already committed and cannot be rolled back → its value is wrong forever.
Recoverable with
cascading rollback		Tj reads the uncommitted value of Ti; commit of Tj is delayed until Ti commits or aborts.Ti aborts → Tj is still uncommitted, so Tj can also be rolled back (cascade).
Cascadeless
(cascade-free)		Tj reads the value of Ti only after Ti has committed.No other transaction has read uncommitted data, so no cascading rollback is needed.

Same schedule, three timings

CaseCommit orderVerdict
T2 commits earlyT2 commits while T1 is still uncommitted; T1 fails laterIrrecoverable — T2 cannot be rolled back
T2 waitsT2's commit is delayed until T1 commits or abortsRecoverable with cascading rollback
T2 reads after T1 commitsT1 commits first, then T2 reads and commitsCascadeless — no cascade needed

How to check any schedule

Method 1 — serializability first. If the schedule is conflict serializable, it is surely recoverable. If not, it may or may not be recoverable, so continue.

Method 2 — dirty-read test. A dirty read = reading a value written by an uncommitted transaction.

  • No dirty read ⇒ surely recoverable.
  • Dirty read exists: if the reader commits before the writer commits/aborts ⇒ irrecoverable; if the reader's commit is delayed until then ⇒ recoverable.

Thumb rules to quote

All conflict-serializable schedules are recoverable. All recoverable schedules may or may not be conflict serializable. Non-serializable schedules may or may not be consistent, and may or may not be recoverable.

4§S04 Why Concurrency Control? source 3.2.5

Definitions

Concurrent execution: in a multi-user system, several users execute operations on the same database at the same time, in an interleaved manner. Concurrency control is the management procedure that controls this concurrent execution so that consistency is preserved.

The four classic problems Must learn

ProblemConflictWhat goes wrongSource example (balance $300)
Lost updateW–WTwo transactions read the same item and update it; the second write overwrites the first, so the first update is lost.TX reads 300, computes 250; TY reads 300, computes 400; TX writes 250; TY writes 400 → 250 lost.
Dirty read
(uncommitted dependency)		W–RA transaction reads an item updated by another transaction that has not committed and later rolls back.TX writes 350; TY reads 350; TX rolls back to 300 → TY holds a value that never existed.
Unrepeatable read
(inconsistent retrieval)		W–RWithin one transaction, the same item is read twice and gives two different values because another transaction updated it in between.TX reads 300; TY updates to 400 and commits; TX reads again → 400.
Incorrect summary
(phantom / inconsistent analysis)		W–ROne transaction aggregates all instances of a repeated item while another updates some instances; the summary matches no consistent state.Sum computed over rows while another transaction inserts/updates rows → total is neither the old nor the new total.

Why allow concurrency at all?

  • Improved throughput — while one transaction waits for a disk page, the CPU executes another transaction (I/O overlaps CPU work). Throughput = transactions completed per unit time.
  • Reduced waiting time — a short transaction interleaved with a long one finishes quickly instead of queueing behind it.

Interleaving must be controlled: uncontrolled interleaving of transactions on the same data item produces the four problems above. Transactions on different items may interleave freely.

What concurrency control must deliver

  • Isolation through mutual exclusion between conflicting transactions.
  • Resolution of read–write and write–write conflicts.
  • Preservation of database consistency and serializability.
  • Atomicity, consistency, isolation, durability for concurrent execution.

Protocol families: lock-based · two-phase locking · timestamp-based · validation (optimistic).
